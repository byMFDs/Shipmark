# Як міняти тексти, переклади, назву і логотип

Усі команди виконуються в папці проєкту, з активованим середовищем:

```bash
cd ~/shipmark
source .venv/bin/activate
```

## Глосарій (єдині терміни в усіх мовах)

Назви позначок на SVG-бейджах завжди англійські: **Repo owner, Domain verified, Steady** (бейджі не перекладаємо).
У нових мовах на сайті теж лишаємо англійською *Repo owner / Domain verified / Steady*; українською вони «Власник репозиторію», «Домен підтверджено», «Стабільний».

## 1. Назва сайту, контакти, гасло

Файл: `config/branding.py`.

- `SITE_NAME` — назва сайту у звичайному тексті й заголовках сторінок (зараз «Shipmark» з великої). У самому логотипі слово пишеться малими літерами («shipmark»): це окремі файли, див. розділ 2.
- `SITE_DOMAIN` — адреса без `https://` (зараз `shipmark.me`). Показується у футері, на бейджах і в коді для вставки.
- `TAGLINE` — гасло. Воно в `_("...")`, тобто перекладається (див. розділ 3).
- `CONTACT_EMAIL`, `LEGAL_OWNER_NAME` — пошта та імʼя власника. Пошта: юридичні сторінки, сторінка бану, скарги й апеляції.
  `LEGAL_OWNER_NAME` стоїть у футері («© 2026 …», звичайними літерами, як написано) **і** в текстах privacy/terms
  («сервіс веде …», «угода між вами і …»), тому там має бути справжнє імʼя людини чи назва компанії, а не гасло.
  `CONTACT_EMAIL` — публічна адреса. Куди приходять **сповіщення про звернення в підтримку** — інше налаштування:
  `SUPPORT_INBOX_EMAIL` у `.env` (див. розділ 8 і `docs/DEPLOY_NOTES.md`).
- `SOCIAL_LINKS` — посилання на соцмережі у футері (під гаслом). Приклад: `{"GitHub": "https://github.com/..."}`.
- `VERIFY_TOKEN_NAME` — назва TXT-запису й метатегу для підтвердження домену (`shipmark-verify`). **Після запуску не змінюй**: усі підтверджені домени не пройдуть наступну перевірку й втратять «Domain verified».

Після зміни перезапусти `runserver` (Ctrl+C і знову `python manage.py runserver`).

## 2. Логотип

Підмінюєш файли в `static/brand/` (імена не змінюй):

| Файл | Де використовується |
|---|---|
| `logo.svg` | шапка сайту (колір бере з теми, тож у SVG краще один колір або `currentColor`) |
| `logo-mark.svg` | знак без напису |
| `logo-dark.svg`, `logo-mark-dark.svg` | світлі копії для темної адмінки (форма та сама: міняй разом із основними) |
| `favicon.svg` | іконка у вкладці браузера |
| `apple-touch-icon.png` | іконка на домашньому екрані iPhone (180×180) |
| `og-default.png` | картинка для превʼю посилання в месенджерах (1200×630). Текст («Less claim. More shipped.», три позначки з «Repo owner») намальований прямо в картинці: змінюєш назву чи гасло, заміни і файл |

Усі іконки малюються з того самого знака (логотип C). `favicon.svg`, `logo.svg`, `logo-mark.svg` (і `-dark` копії)
міняєш руками; `favicon.ico` (16/32/48 px) і `apple-touch-icon.png` після зміни `logo-mark.svg` перемалюй командою:

```bash
python manage.py make_icons
```

Тест `pages/test_brand.py` впаде, якщо забудеш. `og-default.png` має текст усередині, його роби окремо.

**Чому у вкладці був старий логотип.** Браузери зберігають фавікон в окремому кеші й часто не перевіряють файл
знову, якщо його адреса не змінилася (Ctrl+Shift+R це не завжди лікує). Тепер адреса іконки містить відбиток файлу
(`favicon.svg?v=3f2a…` локально, `favicon.3f2a….svg` на сервері), тож нова картинка = нова адреса.

Шрифти (Manrope для заголовків, Inter для тексту, IBM Plex Mono для підписів) лежать у `static/fonts/`, підключені в `static/css/base.css` (`@font-face`). Кольори й розміри — у `static/css/tokens.css` (світла й темна теми; кожне значення там у трьох місцях, міняй усі). Після зміни кольорів перерахуй контраст за таблицею в `docs/DESIGN.md`.

## 3. Короткі тексти інтерфейсу (кнопки, меню, підписи)

Англійський текст — це «першоджерело». Він написаний прямо в шаблонах і Python-коді:

- у шаблонах (`templates/...html`): `{% translate "Sign in with GitHub" %}`
- у Python (`*.py`): `_("Feed")` або `gettext("Feed")`

**Змінити англійський текст:** відредагуй рядок у шаблоні/коді. Потім онови переклад (крок нижче),
бо старий український рядок більше не знайде пару.

**Змінити або додати український переклад:**

1. Витягни нові рядки в файли перекладів **усіх мов одразу** (інакше в інших мовах нові рядки
   просто не зʼявляться і сайт тихо покаже англійську; так сталося під час редизайну):
   ```bash
   python manage.py makemessages -l uk -l pl -l de -l es -l fr -l pt_BR --ignore=.venv --ignore=staticfiles
   ```
2. Відкрий `locale/uk/LC_MESSAGES/django.po`. Кожен рядок виглядає так:
   ```
   msgid "Sign in with GitHub"
   msgstr "Увійти через GitHub"
   ```
   `msgid` — англійський оригінал (його **не чіпай**), `msgstr` — твій переклад.
   Порожній `msgstr ""` означає «не перекладено», тоді покажеться англійська.
   Якщо над рядком стоїть `#, fuzzy`, переклад «під сумнівом» і не використовується:
   перевір його і видали цей рядок з `#, fuzzy`.
   Слова на кшталт `%(name)s` залишай як є: туди підставляється значення.
3. Скомпілюй:
   ```bash
   python manage.py compilemessages --ignore=.venv
   ```
4. Перезапусти `runserver`. Без компіляції (крок 3) зміни не зʼявляться.

Файл `django.mo` — це результат компіляції. Його теж коміть у git, щоб сервер не потребував `gettext`.

## 4. Довгі сторінки (про проєкт, юридичні, FAQ)

Це звичайні Markdown-файли:

```
content/en/about.md     — англійська версія
content/uk/about.md     — українська версія
content/pl|de|es|fr|pt-br/about.md — інші мови (папка `pt-br` — з дефісом)
content/<мова>/how-proof-works.md — «Як працюють підтвердження» (/how-proof-works/)
content/<мова>/privacy.md — Політика конфіденційності (/legal/privacy/)
content/<мова>/terms.md   — Умови користування (/legal/terms/)
content/<мова>/cookies.md — Політика cookies (/legal/cookies/)
content/<мова>/community-rules.md — Правила спільноти (/community/rules/)
```

Відкриваєш файл, міняєш текст, зберігаєш, оновлюєш сторінку в браузері. Перезапуск не потрібен.

- Перший рядок виду `# Заголовок` стає заголовком сторінки і назвою вкладки.
- Якщо українського файлу немає, показується англійський.
- Дозволено: заголовки, списки, **жирний**, *курсив*, посилання, цитати, код, таблиці.
  Сирий HTML і `<script>` видаляються автоматично.
- Якір для посилання на розділ: `## Заголовок {#anchor}` (латиницею). Сторінка проєкту посилається
  на `/how-proof-works/#authored`, `#live`, `#steady`, тож ці три якорі не перейменовуй.
- Сторінка «Як працюють підтвердження» має описувати те, що реально робить код. Якщо змінюєш правила
  в коді (наприклад, 35 днів чи 95%), онови й обидва файли.
- Нова сторінка: створи `content/en/<назва>.md` (латиниця, цифри, дефіс) і додай маршрут
  у `pages/urls.py` за зразком `/about/`. Поки що це робить Claude Code окремим завданням.
- У тексті можна писати підстановки, вони беруться з `config/branding.py` і налаштувань:
  `{{ site_name }}`, `{{ contact_email }}`, `{{ legal_owner_name }}`, `{{ terms_version }}`.
  Пиши їх точно так, з пробілами всередині дужок.

### Юридичні сторінки

- Вони мають описувати **те, що реально робить код**. Основа для них — `docs/DATA_INVENTORY.md`
  (усі персональні дані: що, звідки, навіщо, скільки зберігаємо, хто бачить). Якщо код починає
  зберігати щось нове, спершу онови інвентар, потім тексти.
- Вгорі кожної сторінки є примітка «Draft, last updated …». Після перевірки юристом прибери слово
  «Draft» і фразу про юриста, а дату міняй при кожній зміні тексту.
- Перед запуском заповни в `config/branding.py` справжні `CONTACT_EMAIL` і `LEGAL_OWNER_NAME`.

**Змінилися Умови (terms.md)?** Відкрий `config/settings/base.py` і зміни `TERMS_VERSION` на дату
зміни, наприклад `"2027-03-01"`. Після перезапуску кожен, хто увійшов, при наступному візиті побачить
сторінку «Ми оновили Умови» і має їх прийняти. До прийняття відкриті лише юридичні сторінки,
вихід, завантаження даних і видалення акаунта. Для дрібних виправлень (опечатка) версію не міняй.

## 5. Як працює вибір мови

Порядок: збережена мова в акаунті → cookie (вибір через перемикач у футері) →
мова браузера (`Accept-Language`) → англійська. За IP мова не визначається.

Перемикач у футері працює і без JavaScript, і повертає на ту саму сторінку.
Мови зараз: en, uk, pl, de, es, fr, pt-br. Російську не додаємо.

Додати нову мову: у `config/settings/base.py` допиши її в `LANGUAGES`, потім
`makemessages -l <код>` (для pt-br: `-l pt_BR`), переклади, `compilemessages`.
У `.po` вистав `Plural-Forms` для мови. Створи `content/<код>/` з усіма п'ятьма .md файлами
(about, how-proof-works, privacy, terms, cookies). Для польської потрібен шрифт latin-ext (вже підключений в `base.css`);
для інших алфавітів (грецька, турецька тощо) перевір, чи є потрібні гліфи.

Юридичні сторінки в нових мовах починаються з примітки «Translation for convenience;
the English version prevails» (другий абзац у блоці `>` угорі файлу). Не видаляй її.
Тест `pages/test_translations.py` падає, якщо якийсь рядок із коду відсутній хоч в одній мові, якщо є порожній
чи `fuzzy` переклад, якщо `.mo` не перекомпільовано, або якщо на головних сторінках якоїсь мови лишився англійський текст.
Тест `pages/test_languages.py` перевіряє: усі файли на місці, плейсхолдери `{{ ... }}`, якорі `{#...}`
і посилання збігаються з англійською, а `.po` без порожніх перекладів.

## 6. Сторінки помилок і журнал помилок

**Тексти сторінок помилок** (404 «No record found», 500 «Something broke on our side», 403, 400, «форма застаріла»)
лежать у `templates/404.html`, `403.html`, `500.html`, `400.html`, `403_csrf.html`. Це звичайні `{% translate %}`,
переклад — як у розділі 3. Подивитися всі сторінки, поки `DEBUG` увімкнено: відкрий `/styleguide/` і натисни
посилання «Error pages» (або одразу `/_dev/errors/404/`, `/_dev/errors/500/`, `/_dev/errors/403/`, `/_dev/errors/400/`,
`/_dev/errors/csrf/`). Локально при справжній помилці Django показує свою жовту сторінку з деталями — це нормально,
на сервері її не буде.

**Журнал помилок.** Коли на сайті щось ламається, сервер дописує рядок у файл `logs/errors.jsonl` (на сервері — у папку
з `LOG_DIR`). Сторінки, яких не знайдено (404), ідуть в окремий `logs/notfound.jsonl`. Подивитися зручно командою:

```bash
python manage.py show_errors              # останні 20 помилок, згруповані за типом
python manage.py show_errors --summary    # коротко: скільки разів, коли вперше й востаннє, на яких адресах
python manage.py show_errors --full       # разом із traceback (де саме в коді впало)
python manage.py show_errors --notfound   # які неіснуючі адреси відкривали найчастіше
```

На сторінках 500, 403 і «форма застаріла» внизу є «Reference: 3f9a1c2e». Якщо хтось надішле тобі цей код, знайди
рядок так: `grep 3f9a1c2e logs/errors.jsonl`.

У журнал **ніколи** не потрапляють IP-адреси, дані браузера, cookies, те, що людина ввела у форму, частина адреси
після `?`, пошта, імена користувачів (у шляху `/u/<імʼя>/` стає `/u/[user]/`) і все, схоже на пароль чи токен.
Якщо додаєш новий `logger.error(...)` у коді, не передавай туди такі дані: фільтр їх прибирає, але краще не покладатися.
Файли самі обрізаються: максимум 5 МБ і 5 старих копій кожного.

## 7. Спільнота (форум)

Вмикається змінною `COMMUNITY_ENABLED` у `.env` (`true` / `false`). Вимкнено: усі сторінки `/community/` дають 404,
посилання в меню немає. У розробці вона увімкнена.

- **Правила:** `content/<мова>/community-rules.md`, як і інші довгі сторінки (розділ 4). Короткі правила праворуч на
  кожній сторінці спільноти — це рядки інтерфейсу в `templates/community/_rules_panel.html` (розділ 3). Якщо міняєш
  правило, онови обидва місця.
- **Розділи (boards):** в адмінці, у списку Boards: назва, опис, порядок, «активний». П'ять стандартних розділів
  перекладаються самі (їхні назви є в `community/boards.py` і в `.po`). Новий розділ, створений в адмінці,
  показується так, як ти його написав, без перекладу. Розділ із тредами не видаляй, а зроби неактивним.
- **Стікери:** файли `static/stickers/<ключ>.svg` (96×96, лише фігури й кольори, без тексту, скриптів і посилань) і
  список `community/stickers.py` (ключ → назва). Новий стікер: додай файл, рядок у список, переклади назви
  (`makemessages` / `compilemessages`) і запусти `python manage.py test community`: тест перевіряє, що кожен ключ
  має файл і навпаки, і що SVG безпечний. Ключ старого стікера не видаляй, якщо ним уже користувалися: такі відповіді
  просто не покажуть картинку.
- **Привітальний тред:** `python manage.py post_welcome` публікує закріплений тред «Welcome and rules» від імені
  офіційного акаунта shipmark (один раз). Текст у `community/management/commands/post_welcome.py`, англійською,
  як і всі дописи (дописи не перекладаємо; посилання на правила відкриє їх мовою читача). Новий текст:
  зміни файл і запусти `post_welcome --force` (старий тред відкріпиться).
- **Демо-дані для перегляду сторінок:** `python manage.py seed_community` (лише при `DEBUG`, тобто в розробці).
  Створює людей `demo-…`, треди, відповіді, картинки й голоси. Ще раз — замінює їх, `--clear` — прибирає.
- **Щоденне прибирання:** `python manage.py community_daily` (у продакшені — cron, див. `docs/DEPLOY_NOTES.md`).

## 8. Футер, підтримка, бейджі, лічильник людей

**Футер.** Колонки й посилання — список `FOOTER_COLUMNS` у `pages/templatetags/ui.py` (заголовок колонки і пари
«адреса — підпис»). Підписи англійською в `_("...")`, переклади в `.po` (розділ 3). Посилання зʼявляється саме, щойно
сторінка існує; «Community» — лише коли `COMMUNITY_ENABLED`. Логотип, домен і гасло беруться з `config/branding.py`,
копірайт — з `LEGAL_OWNER_NAME` (рік ставиться сам). Розмітка: `templates/includes/site_footer.html`, вигляд:
розділ «Site footer» у `static/css/components.css`.

**Підтримка.** Тексти сторінки (теми, «що буде далі») — `templates/support/form.html`, сторінка «надіслано» —
`templates/support/sent.html`. Теми (Bug, Idea or feedback …) — `SupportMessage.Category` у `support/models.py`
(нову тему додає Claude Code, бо потрібна міграція). Куди приходить лист — `SUPPORT_INBOX_EMAIL` у `.env`; без неї
повідомлення просто чекають у адмінці (Support → Inbox). Читати інбокс можуть суперкористувач і персонал із дозволом
`support | support message | Can view` (видається в адмінці на сторінці людини, розділ «Permissions»).

**Бейджі (офіційний акаунт, модератор).** Видає суперкористувач в адмінці (Users → Badges) або командою
`python manage.py grant_badge`. Дата на бейджі — справжня дата видачі. Тексти віконця, яке відкривається по кліку, —
`templates/includes/badge_popover.html`; пояснення для всіх — розділ `## … {#badges}` у `content/<мова>/how-proof-works.md`.

**Лічильник «N people joined» у шапці.** Рахує активні акаунти без системного `shipmark` (правило — функція
`count_people` у `pages/stats.py`), оновлюється раз на хвилину. Щоб сховати його, доки людей мало, впиши в `.env`
`PUBLIC_USER_COUNT_MIN=50`: лічильник зʼявиться, коли людей стане більше за 50. Без цього рядка поріг 0.
